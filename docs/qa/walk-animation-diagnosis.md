# 이동 애니메이션 시각 진단 (M1 게이트 플레이테스트 후속)

> 배경: 플레이테스터 피드백 "이동 시 빙글빙글 도는 느낌". 원인 미확정 상태로 접수됨.
> 작성: art-director. 검증 방법: 헤드리스 Godot(`Godot_v4.4.1-stable`, `--display-driver x11
> --rendering-driver opengl3`, Xvfb 오프스크린)로 `Player.tscn`을 실제로 인스턴스화해
> `walk_down/left/up/right` 각 4프레임을 뷰포트째 렌더링 → PNG로 저장 후 육안 확인.
> 렌더링에 쓴 임시 스크립트는 프로젝트 파일이 아니라 세션 스크래치패드에만 두었고(`.gd`/`.tscn`
> 미수정 원칙 준수), 게임 코드는 전혀 건드리지 않았다.

## 결론 요약

**프레임 내용(에셋)과 SpriteFrames 좌표 매핑은 정상이다.** "빙글빙글 도는 느낌"은 소스 이미지가
깨졌거나 좌표가 잘못 잘렸기 때문이 아니다. 유력한 원인은 **① 이 에셋 자체의 태생적 한계(아래/위
방향 그림이 서로 거의 구분되지 않음)와 ② 대각선 입력 근처에서 4방향 중 어디를 재생할지 결정하는
코드 로직에 완충(hysteresis)이 없다는 점의 조합**으로 추정된다. ②는 코드 쪽이라 godot-engineer
확인이 필요한 사항으로 아래 3장에 남긴다.

## 1. 프레임 내용 확인 — 정상

`docs/art/preview/walk-anim-render-m1gate.png`는 실제 게임 씬(Player.tscn)을 헤드리스로 띄워
`walk_down/left/up/right` 각 4프레임을 순서대로 렌더링한 결과다.

- 각 방향 모두 프레임 0→3에서 발/다리 위치가 자연스럽게 바뀐다(양발 대칭 → 한쪽 발 강조 →
  반대쪽 강조를 오가는 전형적인 4프레임 걷기 루프). 정지된 프레임이 반복되거나, 프레임이 깨지거나,
  순서가 뒤섞인 흔적은 없다.
- `Player.tscn`의 `AtlasTexture.region` 좌표(행=방향 고정, 열=프레임)는 원본
  `SpriteSheet.png`(64×112, 4열×7행)의 실제 방향별 행과 픽셀 단위로 정확히 일치한다(Python으로
  `SeparateAnim/Walk.png`와 바이트 비교 완료). **이는 과거 `docs/art/sprite-layouts-m1.md` 1.2절이
  지적했던 "행/열이 뒤바뀐" 문제가 이미 수정되어 있다는 뜻이다** — 현재 좌표는 문서가 제안한 수정안과
  동일하다. 즉 "매 프레임 다른 방향처럼 보이는" 구버전 버그는 재발하지 않았다.

## 2. 에셋 자체의 한계 — down과 up이 거의 구분되지 않음

`row_down.png`/`row_up.png`(스크래치패드 확대본, 좌표는 `docs/art/sprite-layouts-m1.md` 1.3절과
동일)를 나란히 보면, 이 탑다운 데포르메 그림체에서 **아래(down)와 위(up) 방향 프레임이 육안으로
거의 구분되지 않는다**(투구 형태만 미세하게 다름, 발 위치는 동일 — 픽셀 유사도 0.935, 조사
완료 사항 그대로). 반면 좌(left)/우(right)는 옆모습 실루엣이 뚜렷이 달라 방향이 잘 드러난다.

이 자체는 "버그"가 아니라 **CC0 임시 팩의 태생적 한계**다(원작 32×48 전환 시 자연히 해소).
다만 이 특성이 아래 3장의 코드 이슈와 겹치면 체감 문제를 키울 수 있다.

## 3. 코드 쪽 확인 필요 사항 (godot-engineer 인계, 이 세션에서는 수정하지 않음)

`game/scripts/player/player.gd`의 방향 결정 로직:

```gdscript
func set_facing(input_dir: Vector2) -> void:
	if input_dir == Vector2.ZERO:
		return
	if absf(input_dir.x) >= absf(input_dir.y):
		facing = Vector2.RIGHT if input_dir.x > 0.0 else Vector2.LEFT
	else:
		facing = Vector2.DOWN if input_dir.y > 0.0 else Vector2.UP
```

이 함수는 `|x| >= |y|`를 경계로 4방향 중 하나를 매 물리 프레임 다시 계산한다(`move.gd`의
`physics_update()`가 매 프레임 호출). **완충 구간(hysteresis)이 없다** — 입력 벡터가 대각선
45° 부근에서 미세하게 흔들리면(게임패드 아날로그 스틱 드리프트, 또는 대각선 방향 전환 순간의
입력 타이밍) `facing`이 프레임마다 좌↔우 또는 상↔하가 아니라 **수평↔수직 축 자체를 오가며
토글**될 수 있다.

이것이 왜 "빙글빙글 도는 느낌"으로 체감될 수 있는지가 2장의 발견과 맞물린다: down/up은 서로
거의 같아 보이지만, down(또는 up)에서 left/right로 넘어가면 실루엣이 완전히 다르게 바뀐다(정면형
↔ 측면형). 대각선 근처에서 `facing`이 프레임마다 이 두 그룹 사이를 오간다면, 캐릭터가 매 프레임
"정면 ↔ 옆모습"을 빠르게 오가는 것으로 보이고, 이는 정지된 애니메이션이 매끄럽게 순환하는 것과는
전혀 다른 인상 — 방향이 홱홱 뒤집히는 "스핀"처럼 읽힐 수 있다.

**확인 요청 (godot-engineer)**:
1. 실제 플레이 중 `facing` 값을 프레임마다 로깅해(또는 브레이크포인트로) 대각선 이동 시 토글
   빈도를 확인해 달라. 특히 게임패드 아날로그 입력에서 재현 여부.
2. 재현되면 `set_facing()`에 완충 로직(예: 이전 축을 유지하려면 새 축이 일정 비율 이상 우세해야
   전환 — `absf(input_dir.x) >= absf(input_dir.y) * 1.3` 같은 비대칭 임계값) 추가를 검토해 달라.
   이 문서는 원인 후보를 제시하는 데까지이며, 실제 수정 여부·방식은 게임플레이 반응성에 미치는
   영향을 고려해 godot-engineer가 판단할 사항이다.
3. 코드 쪽에 문제가 없는 것으로 확인되면(토글이 재현되지 않으면), 2장의 "down/up 구분 약함"만으로
   설명이 되는지 실제 플레이로 재확인이 필요하다 — 이 경우 원작 32×48 전환(방향별 실루엣을 더 뚜렷하게
   그리는 것) 전까지는 근본 해결이 어렵다는 뜻이므로 우선순위 판단을 디렉터에게 요청한다.
