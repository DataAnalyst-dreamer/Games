## 0. 진행 전 확인 사항 — 알려진 코드 결함 2건 (측정치 해석 시 반드시 감안)

> **[확인 완료 2026-09-08]** 아래 Major 2건은 M1-3(PR #7)에서 수정·검증됨 — 몬스터 후딜은 `RECOVER` 상태 신설로 적용(스모크 `SmokeRabbitDash` "ATTACK→RECOVER 전이" PASS), 히트스톱 중 입력 차단은 스프라이트만 정지하도록 수정(스모크 `SmokeHitstopComboInput` "콤보 2타 연결" PASS). 테스트 결과는 §6 수치 조정 관점으로 해석해도 된다.

`docs/qa/review-m1-1-m1-2.md`가 보고한 Major 2건은 이번 플레이테스트 결과를 오염시킬 수 있는
혼입 변수(confounder)다. **테스트 시작 전 release-manager에게 수정 여부를 확인**하고, 미수정
상태로 테스트를 진행한다면 아래 두 가지를 사전에 감안한다.

1. **몬스터 공격 후딜레이(`attack_recovery_sec`) 사실상 미적용**(`monster_base.gd:158-163`,
   `state`를 `_enter_state()` 없이 직접 대입) — 플레이어가 몬스터 근접 사거리 안에 계속 머무르면
   후딜 없이 예고→공격이 반복될 수 있다. 시나리오 ①·②에서 "몬스터가 쉴 새 없이 계속 공격한다"는
   불만이 나오면 이 버그가 원인일 가능성이 높다 — **수치(예고시간·후딜 값) 문제로 오판해 §5
   조정 후보표를 잘못 적용하지 않도록 주의**.
2. **히트스톱 중 플레이어 자신의 입력이 차단**(`hitstop.gd`/`hit_feel.gd` — `process_mode
   DISABLED`가 `_unhandled_input`까지 막음) — 적이 사거리 경계에 있거나 이동 중(뿔토끼 돌진 등)일
   때 콤보 입력 버퍼 구간(활성 마지막 0.2초)과 히트스톱 데드존이 겹치면 그 프레임의 재입력이
   씹힌다. 시나리오 ①에서 "분명히 눌렀는데 콤보가 안 이어진다"는 자유 서술이 나오면 §4(콤보)
   질문 응답과 별개로 이 버그를 의심할 것.

두 건 모두 **수치 조정으로 해결되지 않는 로직 버그**이므로, 평가지 자유 서술에 유사 증상이
2건 이상 모이면 §5 조정 대신 **godot-engineer에게 review-m1-1-m1-2.md Major-1/2 수정을 먼저
요청**한다.

## 1. 빌드 준비 절차 (개발자용)

### 1-1. 머지 순서
PR #3(M1-0 스캐폴드) → #5(M1-1 전투 기초) → #6(M1-2 구르기/가드/사망) → M1-3(몬스터 3종·사운드,
현재 `stage/m1-3-monsters-audio`, 이 브랜치가 기본 브랜치로 PR·머지된 뒤) 순서로 기본 브랜치
(`claude/dot-action-rpg-design-cwwlgc`)에 반영되어 있어야 한다. 테스터에게 전달할 빌드는 **M1-3
머지 이후 커밋**을 기준으로 한다 — 몬스터 3종(슬라임/뿔토끼/버섯돌이)과 AudioManager가 이 단계
이전에는 존재하지 않는다.

### 1-2. Godot 4.4.1 로컬 실행 방법
`export_presets.cfg`가 아직 작성되지 않아 Windows/Mac 실행 파일 익스포트는 M1 단계에서 지원하지
않는다. **에디터 실행이 유일한 전달 방식**이다.

1. 테스터 PC에 Godot **4.4.1**(gl_compatibility 렌더러 빌드) 설치.
2. 저장소를 clone(또는 zip 전달) 후 Godot 실행 → "Import" → 저장소의 `game/project.godot` 선택.
3. 최초 1회는 임포트가 끝날 때까지 대기(폰트 등 첫 임포트에서 `Parameter "fd" is null` 경고가
   여러 줄 찍힐 수 있음 — 두 번째 실행부터 사라지는 정상 현상, `game/README.md` 참고).
4. 에디터 상단 **F5**(또는 재생 버튼) → 메인 씬(`scenes/main/Main.tscn`)이 자동 실행.
5. 실행 중 콘솔(에디터 하단 Output 패널)을 열어 둔다 — §4 측정 항목의 로그 확인용.

### 1-3. 테스터 전달용 조작표 (GDD 4.1 + `game/README.md` 기준, 키보드·패드 병기)

| 액션 | 키보드·마우스 | 패드(Xbox 레이아웃) |
|---|---|---|
| 이동 (8방향) | WASD / 화살표 | 왼쪽 스틱 |
| 기본 공격 (3타 콤보) | 마우스 좌클릭 | X |
| 강공격 (M1 미구현 — 입력해도 반응 없음) | 마우스 우클릭 | RT |
| 구르기 (무적 0.3초) | Space | B |
| 가드 (누르는 동안 유지, 적중 직전 0.1초 내 입력 시 저스트 가드) | Shift | LT |
| 상호작용 (비석 활성화) | F | A |
| 스킬 슬롯 1·2 (M1 미구현) | Q / E | LB / RB |

- 모바일 가상 스틱/버튼은 M1 빌드에 없음(GDD D-06, M2 이후).

## 2. 테스트 시나리오 4개 (각 5~10분)

공통 준비: `godot --path game`(또는 에디터 F5)로 실행하면 슬라임 3·뿔토끼 2·버섯돌이 1·비석 1이
겹치지 않게 배치돼 있다(`game/README.md`). 화면 하단 `DebugHud`가 HP/스태미나·상태 플래그
(`GUARD`/`JUST-GUARD!`/`ROLL`/`IFRAME`)·사망 횟수를 실시간 표시하니 테스터에게 미리 보는 법을
알려준다.

### 시나리오 ① 슬라임 3마리 — 3타 콤보·히트스톱·넉백 체감 (5분)
- **테스터 지시문**: "맵 중앙 근처 슬라임 3마리를 전부 처치해 주세요. 콤보를 3타까지 끝까지
  밀어붙여 보고, 2타에서 멈춰도 보세요."
- **관찰 포인트**: 타격 시 정지감(히트스톱)이 느껴지는지, 맞을 때마다 슬라임이 밀려나는지(넉백
  8px), 3타(피니셔)가 1·2타보다 "묵직하다"고 느끼는지, 후딜(0.35초) 동안 다음 슬라임에게 무방비로
  노출되는 느낌이 과한지.
- **로그로 확인**: `hit_landed` 시그널 발생 횟수·간격(콘솔에 디버그 출력이 없다면 §4-4 참고,
  godot-engineer 요청 사항), `enemy_died` 3회(슬라임 개체 수만큼), 각 개체 TTK가 2타 목표(약
  0.5~0.6초, 콤보 1·2타 기준)에 근접하는지.

### 시나리오 ② 뿔토끼 — 예고 읽기·구르기 무적 타이밍 (7분)
- **테스터 지시문**: "뿔토끼에게 접근해 돌진 예고(웅크림, 약 0.6초)를 보고 정면에서 구르기로
  받아보세요. 5회 이상 시도해 보고, 그중 몇 번 맞았는지 세어 주세요."
- **관찰 포인트**: 웅크림 동작이 "곧 무언가 온다"는 신호로 명확히 읽히는지, 예고 시작 후 0.2~0.5초
  구간(예고의 60%)에 구르기를 입력하면 대체로 회피에 성공하는지, 너무 일찍 구른 경우(예고 초반)
  후딜 중 피격되는 실패 패턴이 나오는지, 돌진이 벽에 부딪혀 기절(`STUNNED`, 0.5초)했을 때 반격
  기회로 이어지는지.
- **로그로 확인**: 무적(`IFRAME`) 플래그 표시 중 `player_damaged` 발생 여부(발생하면 §4의 "구르기
  실패" 사례, 0건이 목표), 돌진 시작~적중까지 실측 시간(설계값 0.6초 예고 + 0.3초 돌진).

### 시나리오 ③ 버섯돌이 — 장판 회피·가드/저스트 가드 (7분)
- **테스터 지시문**: "버섯돌이에게 접촉해 포자 장판을 일부러 밟아본 뒤 빠져나와 보세요. 이어서
  같은 자리에서 가드를 유지한 채 버텨보고, 마지막엔 적중 직전에 Shift를 눌러 저스트 가드를
  시도해 보세요."
- **관찰 포인트**: 장판(반경 32px)의 시각적 경계가 눈에 보이는지, 장판 안에서 구르기로 무적을 얻어도
  지속 피해(1초당 4)가 계속 깎이는지(D-61 예정 — 의도된 동작이니 "버그처럼 느껴지는지"를 물어야
  함, §6 참고), 일반 가드 시 칩데미지(20%)가 나가면서도 스태미나가 줄어드는 게 체감되는지, 저스트
  가드 타이밍(적중 직전 0.1초)이 "외워서 맞출 수 있는" 수준인지 "운에 가까운지".
- **로그로 확인**: `just_guard_succeeded` 발생 시점과 실제 적 공격 타이밍의 오차, 장판 내 무적 중
  `player_hp_changed` 감소 발생(의도된 동작 — 미발생 시 오히려 D-61 미구현 버그로 별도 보고).

### 시나리오 ④ 사망 → 비석 부활 (5분)
- **테스터 지시문**: "비석을 먼저 F키로 활성화한 뒤, 몬스터에게 일부러 여러 번 맞아 사망해
  보세요. 부활까지 몇 초 걸리는지, 부활 직후 체력이 꽉 찬 상태인지 확인해 주세요."
- **관찰 포인트**: 사망 연출(페이드, 1.0초)이 뚝 끊기지 않고 자연스러운지, 부활 위치가 방금
  활성화한 비석인지, HP/스태미나가 전량 회복됐는지, 사망 횟수(`DEATH: n`)가 DebugHud에서 오르는지.
- **로그로 확인**: `player_died` → (1.0초) → `player_respawned` 시퀀스, `GameState.death_count`
  증가량이 실제 사망 횟수와 일치하는지.

## 4. 측정 항목 (자동 수집 가능한 것 / 현재 로그 상태 / 부족분)

| 항목 | 현재 상태 | 얻는 방법 | 부족분 (godot-engineer 요청) |
|---|---|---|---|
| 세션당 사망 횟수 | **가능** | `GameState.death_count`를 DebugHud(`DEATH: n`)가 이미 표시 — 세션 종료 시 화면 캡처 또는 값 구두 보고로 수집 | 없음 |
| 구르기 성공률(무적 중 피격 회피) | **불가(로그 없음)** | 없음 — `Events.player_stamina_insufficient`는 발동 실패만 감지, "구르기는 됐는데 맞았다"는 별도 이벤트가 없음 | `Player.start_iframes()` 활성 구간 중 `Events.player_damaged` 발생 시 "iframe 중 피격" 카운터를 증가시키고, 구르기 진입 횟수(`RollState._enter_state` 등) 대비 비율을 세션 종료 시 콘솔에 `print()`로 요약 출력해 달라는 요청. 최소 구현은 `Roll` 상태 진입 카운트 + iframe 중 피격 카운트 2개 정수 전역 변수로 충분 |
| 저스트 가드 성공률 | **부분 가능** | `Events.just_guard_succeeded`가 이미 emit됨(신규, D-69 예정) — 발생 횟수는 셀 수 있음 | 분모(가드 중 피격 시도 총횟수, 즉 "저스트 실패+일반 가드+무가드 피격"을 모두 포함한 피격 이벤트 수)를 세는 카운터가 없다. `Player._on_hurtbox_hurt()`가 가드 상태 여부를 이미 판별하므로, 여기서 "가드 상태였던 피격 총횟수"와 "그중 저스트 성공 횟수"를 세션 종료 시 함께 출력해 달라는 요청 |
| 평균 TTK | **불가(로그 없음)** | 없음 — `Events.enemy_died(enemy, killer)`는 있지만 교전 시작 시각을 남기는 이벤트가 없다 | 몬스터가 `IDLE`/`PATROL`에서 최초로 `TELEGRAPH`/`CHASE`로 전이하는 시각(교전 시작으로 정의)과 `enemy_died` 시각의 차를 몬스터별로 계산해 `print()`로 남겨 달라는 요청. `monster_base.gd`의 상태 전이 지점에 `Time.get_ticks_msec()` 기록 1줄이면 충분 |
| (공통) 위 로그의 영속화 | **없음** | 현재 `project.godot`에 파일 로깅 설정이 없어(`debug/file_logging/enable_file_logging` 미설정) 콘솔 출력이 세션 종료와 함께 사라질 수 있음 | 테스터 세션마다 로그를 남기려면 `project.godot`에 `debug/file_logging/enable_file_logging=true` 추가(파일은 기본적으로 `user://logs/godot.log`에 쌓임) — 값 1줄 추가로 해결되는 낮은 비용의 요청이니 위 3개 카운터 요청과 함께 처리 권장 |

**요약**: 사망 횟수만 지금 당장 수집 가능하고, 나머지 3개는 godot-engineer에게 위 표의 최소 추가
로깅(카운터 변수 + 세션 종료 시 `print()` 요약, 파일 로깅 설정 1줄)을 요청해야 한다. 코드 작성은
godot-engineer 몫이며 본 문서는 입력(어떤 이벤트/상태 전이를 관찰점으로 쓸지)과 출력(어떤 값을
어떤 시점에 남길지) 명세만 제공한다.

## 5. 합격 기준 (제안, 근거 명시)

**제안 기준**: 10인 평균 타격감(§3-1 5문항 평균) **≥ 4.0** **그리고** 3점 이하 응답 **≤ 2인**.

**근거**:
- 평균 ≥4.0은 GDD 13장·PRD KPI가 명시한 원문 기준을 그대로 채택한다 — 임의 상향/하향 없음.
- "3점 이하 응답 ≤2인" 조건을 추가하는 이유: 평균만으로 합격 판정하면 "10명 중 2~3명이 강하게
  불만족(2점)해도 나머지가 5점을 주면 평균 4.0을 넘길 수 있는" 통계적 맹점이 생긴다. GDD 14장이
  "전투 손맛 미달"을 최우선 리스크로 지목한 만큼, 소수라도 뚜렷한 불만족군이 있으면 그 원인(특정
  조작 방식·특정 몬스터 패턴 등)을 밝히지 않고 다음 단계로 넘어가는 것은 리스크 대응 취지에
  어긋난다. 인원 상한을 "2인"으로 잡은 근거는 10인 표본에서 20%를 임계로 삼는 관례적 기준(품질
  게이트에서 흔히 쓰는 "하위 20% 초과 시 재검토" 규칙)을 원용한 것 — 별도 사내 데이터가 없어
  "제안"으로 표기하며, PM/게임 디자인 리드 확인 후 확정 필요.
- 문항 1·2(맞혔다/맞았다) 평균이 문항 3~5 평균보다 유의미하게 낮다면(예: 0.5점 이상 차이), §0의
  버그 2건 또는 §6의 placeholder 아트 영향을 우선 의심하고 §7 조정표를 바로 적용하지 않는다.

## 7. 알려진 제약 (테스터 사전 안내용)

플레이 시작 전 테스터에게 아래 항목을 짧게 공지해 "버그 신고"와 "의도된 placeholder"를 혼동하지
않도록 한다.

- **캐릭터·몬스터 아트는 임시 대역**: 플레이어는 Knight 시트, 뿔토끼는 Racoon 대역, 버섯돌이는
  Mushroom 대역을 쓴다. 최종 캐릭터 외형이 아니다.
- **가드·구르기 전용 애니메이션 없음**: 구르기는 전용 잔상 이펙트가 없어 현재 스프라이트 프레임을
  복제·페이드하는 방식으로 대체돼 있다(`roll_ghost.gd`). 가드도 별도 자세 애니메이션이 없다.
- **HUD는 디버그용**: 화면 하단 텍스트 HUD(`DebugHud`)는 정식 UI가 아니라 개발자용 수치 표시다.
  "UI가 예쁘지 않다"는 피드백은 이번 게이트의 평가 대상이 아니다.
- **SFX 3건은 sfxr 임시 대체음**: 타격·구르기·가드 등 일부 효과음이 최종 사운드가 아닌 sfxr 생성
  임시음이다(`docs/audio` 사운드 맵 참고). "효과음이 조잡하다"는 의견은 별도로 기록하되 타격감
  리커트 점수 자체에는 영향을 주지 않도록 사전 안내한다.
- **강공격·스킬 슬롯 미구현**: §1-3 조작표 참고. 입력해도 반응 없음은 정상이다.
- **버섯돌이 장판 지속 피해는 무적 중에도 적용됨(의도)**: 구르기/피격 직후 무적 상태에서도 장판
  안에 있으면 계속 깎인다(D-61 예정). 시나리오③에서 "무적인데 왜 맞냐"는 반응이 나올 수 있으니
  질문 시 미리 언급하지 않되, 서술형 답변에 나오면 버그가 아님을 안내한다.
