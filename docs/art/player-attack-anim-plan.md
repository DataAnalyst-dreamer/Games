# 플레이어 공격 애니메이션 계획 (M1 게이트 플레이테스트 후속)

> 배경: 플레이테스터 피드백 "공격 시 몸이 계속 idle 자세인 채 칼 스프라이트만 옆에서 회전한다".
> 원인은 코드로 확인 완료 — `game/scripts/player/states/attack.gd`의 `_start_current_hit()`가
> 매 타 `player.play_anim("idle")`을 호출해 몸 애니메이션을 강제로 idle에 고정하고,
> `player.gd`의 `play_attack_swing()`이 `WeaponPivot`(칼만 있는 별도 노드)을 `facing*8px` 위치에
> 놓고 회전 tween만 준다. 이 문서는 실제 사용 가능한 CC0 자산을 조사해 "몸도 같이 움직이는" 대안을
> 구체적 좌표·타이밍으로 확정한다. **코드(.gd/.tscn)는 이 세션에서 수정하지 않는다** — 아래 표를
> godot-engineer가 그대로 SpriteFrames/상태 스크립트에 반영하면 된다.

## 1. 자산 조사 결론

### 1.1 후보 A — `SpriteSheet.png` 행4(Attack, 4프레임, 단일 방향) — **채택**

`Actor/Character/Knight/SpriteSheet.png`(64×112, 4열×7행, 16px 셀)의 행4(y=64)는
`SeparateAnim/Attack.png`(64×16)와 바이트 단위로 정확히 일치하는, 이미 확정된 4프레임 공격 스윙
포즈다(`docs/art/sprite-layouts-m1.md` §1.1, 이번 세션에서 SamuraiBlue로도 동일 레이아웃
재확인 — 이 팩의 모든 캐릭터가 같은 규칙을 따름).

| 프레임 | region (x, y, w, h) | 포즈 |
|---|---|---|
| 0 | (0, 64, 16, 16) | 윈드업(무기를 들어올리는 시작 자세) |
| 1 | (16, 64, 16, 16) | 스윙 시작(몸을 앞으로 기울임) |
| 2 | (32, 64, 16, 16) | 스윙 정점(가장 낮게 숙인 타격 자세) |
| 3 | (48, 64, 16, 16) | 팔로우스루(자세 풀리는 중) |

**문제**: 이 4프레임은 **단일 방향뿐**이고(정면형 몸통 숙임 동작, 좌우 어느 쪽으로도 뚜렷이
치우치지 않은 포즈), 원본 팩에 상/하/좌/우 각각의 공격 프레임은 존재하지 않는다.

### 1.2 후보 B — `SeparateAnim/Attack.png` + `Walk.png` 4방향 조합 — 기각

다른 캐릭터(SamuraiBlue, Lion)의 `SeparateAnim/Attack.png`도 Knight와 동일하게 64×16(4프레임×
1방향)뿐이며, 이 팩 어디에도 "방향별 Attack" 파일이 없다. `Walk.png`(4방향×4프레임)의 각 방향
포즈를 가져와 "공격"이라고 우기는 방법도 검토했으나, Walk 프레임은 보행 중 자세라 무기를 휘두르는
느낌이 전혀 나지 않아 기각.

### 1.3 방향별 커버 방안 — **행4 프레임을 4방향 전부에 재사용**

상/하/좌/우 전용 공격 프레임이 없으므로 다음 절충안을 채택한다:

- **행4의 동일한 4프레임을 `attack_down`/`attack_left`/`attack_up`/`attack_right` 4개 애니메이션에
  전부 그대로 배정**한다(추가 크롭·좌우반전 없이 같은 AtlasTexture 4장을 재사용). 이 포즈는 몸을
  앞으로 숙이며 내려찍는 범용 동작이라 어느 방향을 보고 있어도 어색하지 않다 — 실제로
  `docs/qa/walk-animation-diagnosis.md`에서 확인했듯 이 팩은 down/up 구분조차 미세해서, 애초에
  "방향별로 다른 공격 실루엣"을 기대하기 어려운 자산이다.
- 방향 구분은 지금처럼 **`WeaponPivot` 회전(= `facing` 기반)이 전담**한다. 몸은 "지금 휘두르고
  있다"는 동작만 보여주고, "어느 쪽으로 휘두르는지"는 계속 무기 스프라이트가 보여주는 역할 분리다.
  이렇게 하면 몸 애니메이션 부재 문제(피드백 ①)와 방향별 자산 부재 문제를 **동시에, 새 자산 없이**
  해결한다.
- **좌우반전(flip_h) 옵션(선택, 우선순위 낮음)**: `attack_left`에 한해 `flip_h=true`를 주면
  행4 프레임의 미세한 비대칭(투구 홈 위치 등)이 반전되어 좌/우가 아주 약간 달라 보인다. 필수는
  아니고, 여유가 되면 godot-engineer 재량으로 추가해도 된다(down/up/right는 `flip_h=false`).

### 1.4 대안 검토 — 새 CC0 팩 도입 / idle+무기회전 유지

- **새 팩 도입**: 방향별 공격 프레임을 갖춘 다른 CC0 16px 팩을 찾아 보강하는 방안도 검토했으나,
  이번 세션에서 그런 팩을 확보하지 못했고, 확보하더라도 Knight와 그림체(선 굵기·비례·팔레트)가
  달라 한 씬에서 이질감이 커진다(`asset-sources.md` §2 "밀도/그림체 혼용 금지" 원칙과도 상충).
  M1 게이트에서는 기각하고, **원작 32×48 도트 제작 시 이 팩 안에서 4방향×4~6프레임을 새로 그리는
  것**을 정식 물량으로 남긴다(`sprite-layouts-m1.md` §1.5에 이미 등재됨, 변경 없음).
- **idle+무기회전 그대로 유지**: 플레이테스터가 명시적으로 지적한 문제라 기각. 위 1.3 절충안이
  추가 자산 없이 즉시 적용 가능하므로 이 대안을 선택할 이유가 없다.

## 2. SpriteFrames 추가 정의 (godot-engineer 반영용)

`Player.tscn`의 `SpriteFrames`(`sprite_frames` 서브리소스)에 아래 4개 애니메이션을 추가한다.
소스는 기존에 이미 로드돼 있는 `ExtResource("1_knight")`(`SpriteSheet.png`)이므로 새 리소스
등록은 필요 없다.

| 애니메이션 이름 | 프레임 순서(region) | flip_h | speed(fps) | loop |
|---|---|---|---|---|
| `attack_down` | (0,64,16,16) → (16,64,16,16) → (32,64,16,16) → (48,64,16,16) | false | **12.0** | **false** |
| `attack_up` | 위와 동일 4프레임 | false | 12.0 | false |
| `attack_right` | 위와 동일 4프레임 | false | 12.0 | false |
| `attack_left` | 위와 동일 4프레임 | true(선택) | 12.0 | false |

- speed 12fps × 4프레임 = **0.333초** — 이는 우연이 아니라 `tuning.gd`의 기존 상수
  `ATTACK_ANIM_FPS(12.0)`/`ATTACK_ANIM_FRAMES(4)`/`ATTACK_HIT_DURATION_SEC(0.333)`와 정확히
  같다. 즉 **새 애니메이션 재생 시간이 이미 코드에 박혀 있는 히트박스 활성 시간과 자동으로
  일치**한다 — 별도 동기화 코드 없이 "스윙 애니메이션 = 활성 판정 구간"이 그대로 맞아떨어진다.
- `loop=false`가 중요하다: Godot `AnimatedSprite2D`는 비반복 애니메이션이 끝나면 **마지막 프레임에
  자동으로 멈춘 채 유지**한다. 즉 피니셔(3타) 후딜(`finisher_recovery_sec=0.35s`) 동안 별도 코드
  없이 프레임3(팔로우스루 포즈)이 그대로 유지된다 — "몸이 idle로 스냅백"하지 않는다.

## 3. 코드 쪽 반영 지점 (권장, 이 세션에서 직접 수정하지 않음)

`game/scripts/player/states/attack.gd`의 `_start_current_hit()`에서:

```gdscript
player.play_anim("idle")          # 현재
player.play_anim("attack")        # 권장 변경 — "attack_<facing>" 재생
```

이 한 줄 교체 + 위 SpriteFrames 4종 추가만으로 피드백 ①(몸이 idle 고정)이 해소된다. 나머지
로직(`play_attack_swing()` 무기 회전, 히트박스 타이밍, 콤보 상태머신)은 값 변경 없이 그대로 둔다.

부가 제안(우선순위 낮음, 이번 요청 범위 밖): `tuning.gd`에 이미 존재하지만 아직 배선되지 않은
`ATTACK_STARTUP_FRAMES(4)`/`ATTACK_RECOVER_TO_IDLE_FRAMES(6)`(`combat.json` 주석 참고 — "실제
애니메이션 자산 확보 전 반영 보류"라고 명시돼 있었음)를 이제 실제 자산이 생겼으니 배선할 수 있다.
다만 이는 콤보 상태머신 타이밍을 건드리는 작업이라 game-designer 확인 후 별도 작업으로 남긴다.

## 4. 무기(칼) 스프라이트 합성 방식 — 오버레이 유지 + 스윙 구간 동기화

행4 프레임 자체에도 무기로 보이는 형체가 희미하게 그려져 있지만(프레임1의 머리 위 세로 막대),
16px 해상도에서 명확한 칼로 읽히지 않는다. 반면 현재 `WeaponPivot`+`WeaponSprite`(Sword
스프라이트 회전) 오버레이는 이미 또렷하게 "칼"로 읽힌다. 따라서:

- **오버레이 방식(현행 `play_attack_swing()`)을 그대로 유지**한다. 몸 프레임에 무기를 새로
  그려 넣어 오버레이를 없애는 방향은 채택하지 않는다(원작 32×48 전환 시 무기를 손에 든 프레임을
  직접 그리는 것이 정공법이나, 그건 별도 물량 — `sprite-layouts-m1.md` §1.5 이미 등재).
- **동기화**: `play_attack_swing(hit_index, duration)`의 `duration` 인자에 위 애니메이션과 같은
  `combo.hit_duration_sec`(=0.333s)이 이미 전달되고 있으므로(`attack.gd` 확인 완료), 몸 스윙 4프레임과
  무기 회전 tween의 총 길이는 이미 일치한다. 프레임 단위로 더 세밀하게 맞추고 싶다면(선택,
  폴리시 단계) 아래 대응표를 참고해 `play_attack_swing()`을 프레임별 키프레임 tween으로 바꿀 수
  있다 — 필수는 아니고, 현재의 단일 연속 tween(시작각→끝각)도 이미 충분히 자연스럽다.

| 몸 프레임(4프레임 중) | 진행률(0~1) | 무기 회전 진행률(1·2타, 70° 스윕 기준) | 비고 |
|---|---|---|---|
| 0(윈드업) | 0% | 0%(시작각, `facing.angle() - 70°`) | 몸이 무기를 들어올리는 순간 = 무기도 시작 위치 |
| 1(스윙 시작) | 25% | ~30% | |
| 2(스윙 정점) | 50~75% | ~70~90% | 몸이 가장 숙인 순간과 무기가 정면을 스치는 순간이 거의 겹침 |
| 3(팔로우스루) | 100% | 100%(끝각, `facing.angle() + 70°`) | 몸·무기 모두 스윙 종료 자세로 함께 도착 |

2타는 무기 회전 방향만 반대(끝각→시작각)이고 몸 프레임 진행률 대응은 동일하게 적용한다. 3타
(피니셔)는 스윕이 110°로 넓어지지만 몸 프레임은 동일한 4장을 그대로 재생 — 진행률 대응표도
동일하게 쓰면 된다(몸 프레임 수가 늘지 않으므로 "더 큰 동작"의 체감은 전적으로 무기 스윕 각도와
히트스탑/카메라 흔들림 등 기존 타격감 연출이 담당).

## 5. 해상도 의견 (아트 관점, 1문단)

현재 640×360 내부 렌더·정수 3배(1920×1080)는 "데스크탑 기준 낮다"는 피드백이 있었지만, 아트
관점에서는 **내부 렌더 해상도 자체를 올리는 것에 반대**한다. 이 스프라이트들은 16px 격자에 그려진
도트이고(캐릭터 16×16, GDD 최종 목표도 32×48 — 어느 쪽이든 저해상도 그림), 내부 해상도를 올리면
정수 배율이 아닌 스케일(예: 640×360→960×540처럼 애매한 배수)이 섞여 들어가 픽셀이 뭉개지거나
셰이더 보정 없이는 도트가 흐릿해진다("한 씬에서 픽셀 밀도를 섞지 않는다" 원칙과도 직결). 체감
해상도가 낮다는 인상은 대부분 **낮은 배율(3배)에서 화면에 보이는 정보량이 적어 보이는 것**과
**16px 자산의 디테일 부족**이 원인이지, 내부 렌더링 해상도 자체의 문제가 아니다. 개선하려면
① 카메라 줌을 조정해 화면에 더 많은 월드가 보이도록 하거나(이미 `sprite-layouts-m1.md` §5.2가
32×48 전환 시 줌 2×→1×/1.5× 조정을 권장해 둠), ② 창 배율을 3배에서 4배로 올려 디스플레이 여백을
줄이는 정도가 아트 자산을 새로 만들지 않고 시도할 수 있는 선이다. 내부 해상도 자체를 640×360보다
올리는 결정은 이후 32×48 원작 전환과 맞물려 재논의하는 편이 낫다(원작 자산 밀도가 확정돼야 몇
배율이 정수배로 맞는지 계산 가능). 최종 결정은 godot-engineer/디렉터 몫으로 남긴다.
