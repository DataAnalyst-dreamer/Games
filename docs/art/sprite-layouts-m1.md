# 스프라이트 레이아웃 조사 — M1 (Knight / Slime / 뿔토끼·버섯돌이 대역)

> 조사 방법: Python(Pillow)로 시트를 직접 열어 픽셀 단위로 대조했다. Ninja Adventure의
> `Actor/Character/<이름>/SeparateAnim/*.png`는 완성된 `SpriteSheet.png`를 만들기 전 애니메이션별로
> 나눠 작업한 원본 조각으로 보이며, 조각 이미지와 합본 시트를 **바이트 단위로 diff**하면 각 조각이
> 합본의 어느 좌표에 들어갔는지 100% 확정할 수 있다. `Actor/Monster/`에는 이 조각 파일이 없어
> Knight만큼 확실하게 확정할 수 없고, 행(row) 간 유사도 계산으로 구조를 추정했다 — 확신도를 등급으로
> 표기했다.
>
> 생성한 확대 미리보기: `docs/art/preview/knight_spritesheet_grid.png`,
> `docs/art/preview/knight_walk_rows_zoom.png`, `docs/art/preview/knight_lr_compare.png`,

## 1. Knight — `Actor/Character/Knight/SpriteSheet.png` (64×112, 16px 셀, 4열×7행)

### 1.1 확정 사실 (SeparateAnim 바이트 diff, 확신도 최고)

`SeparateAnim/*.png`를 합본 시트 위에서 슬라이딩 비교한 결과, 예외 없이 각 조각이 정확히 한
좌표에서만 일치했다:

| 조각 파일 | 크기 | 합본에서의 위치 | 의미 |
|---|---|---|---|
| `Idle.png` | 64×16 (1행×4프레임) | **행0**, 열0~3 전체 | Idle (4프레임) |
| `Walk.png` | 64×64 (4행×4프레임) | **행0~3**, 열0~3 전체 | Walk 블록 전체(4방향×4프레임) — Idle과 행0을 공유 |
| `Attack.png` | 64×16 | **행4**, 열0~3 전체 | Attack (4프레임, 단일 방향) |
| `Jump.png` | 64×16 | **행5**, 열0~3 전체 | Jump (4프레임, 단일 방향) |
| `Dead.png` | 16×16 | **행6, 열0** | Dead (1프레임) |
| `Item.png` | 16×16 | **행6, 열1** | Item (아이템 들기, 1프레임) |
| `Special1.png` | 16×16 | **행6, 열2** | Special1 (1프레임) |
| `Special2.png` | 16×16 | **행6, 열3** | Special2 (1프레임) |

**핵심 결론: 이 시트는 "행(row) = 애니메이션/방향, 열(col) = 프레임"인 행-우선(row-major) 구조다.**
Idle.png(가로로 긴 64×16 한 장)이 정확히 행0 하나에 대응한다는 사실 자체가 이를 증명한다 — 만약
"열 = 방향, 행 = 프레임"이었다면 단일 방향 애니메이션은 세로로 긴(16×64) 이미지여야 하는데
실제로는 가로로 긴 이미지였다.

### 1.2 현재 `game/scenes/player/Player.tscn`과의 불일치 (중요 — godot-engineer 확인 필요)

현재 Player.tscn의 SpriteFrames는 **열(column)을 방향으로, 행(row)을 프레임으로** 취급하고 있다:

```
at_down_0..3  = (x=0,  y=0/16/32/48)   ← 열0 세로 4칸
at_up_0..3    = (x=16, y=0/16/32/48)   ← 열1 세로 4칸
at_left_0..3  = (x=32, y=0/16/32/48)   ← 열2 세로 4칸
at_right_0..3 = (x=48, y=0/16/32/48)   ← 열3 세로 4칸
```

1.1의 확정 사실과 반대 방향이다. 이 매핑대로면:
- `idle_down/up/left/right` 4개 애니메이션이 실제로는 **전부 행0(=하나의 방향) 안에서 프레임만 다르게
  자른 것**이라 캐릭터가 방향을 바꿔도 시각적으로 거의 안 바뀐다 (idle_up=행0열1, idle_left=행0열2,
  idle_right=행0열3 — 전부 같은 Idle 스트립의 다른 프레임일 뿐 다른 방향이 아님).
- `walk_down`(현재 정의 = 열0의 행0~3)은 실제로는 **서로 다른 4개 방향 행에서 한 프레임씩 뽑은 것**이라
  걷는 동안 캐릭터가 매 프레임 다른 방향처럼 보일 수 있다.

**권장 수정** (이미 만들어 둔 16개 AtlasTexture 서브리소스는 전부 재사용 가능 — 좌표 재배치만 필요):

| 애니메이션 | 올바른 좌표(행 고정, 열0~3 순서) |
|---|---|
| `walk_down` | y=0,  x=0/16/32/48 |
| `walk_left` | y=16, x=0/16/32/48 |
| `walk_up`   | y=32, x=0/16/32/48 |
| `walk_right`| y=48, x=0/16/32/48 |
| `idle_down` | y=0, x=0 (1프레임, 필요시 행0 전체 4프레임 루프로 확장) |

행1/행3의 좌/우 배정은 1.3 참고 — 잠정치이며 인게임 확인 후 이름만 바꾸면 된다.

### 1.3 Walk 4행의 방향 배정 (확신도: 행0=Down 높음 / 나머지 중간)

행별 픽셀 유사도(동일 픽셀 비율)를 계산한 결과:

```
행0 vs 행2 = 0.935 (매우 유사 — 둘 다 발이 좌우대칭으로 보이는 "정면형" 포즈)
행1 vs 행3 = 0.865 (유사 — 둘 다 발 하나만 보이는 "측면형" 포즈, 프레임2/3에서 앞발 위치가 서로
                     반대로 나타나 방향이 다른 한 쌍임을 시사)
그 외 조합 = 0.47~0.60 (뚜렷이 다름)
```

- **행0 = Down (확신 높음)**: Idle.png와 바이트 일치 + 이 장르 관례상 기본/정면 포즈가 Down.
- **행2 = Up (확신 중간)**: 행0과 대칭 그룹이므로 소거법상 Up. (Up/Down이 이 데포르메 그림체에서
  거의 같아 보이는 것은 자연스럽다 — 얼굴이 아니라 투구 형태만 보이는 탑다운 시점.)
- **행1·행3 = Left/Right 쌍 (확신 중간)**: 두 행 다 "발 하나 노출형" 실루엣이고, 프레임2·3에서
  강조색(주황/빨강) 위치가 서로 반전되어 있어 좌우 대칭 관계의 두 방향으로 보는 것이 타당하다.
  다만 좌/우 중 **어느 쪽이 Left이고 어느 쪽이 Right인지는 픽셀 비교만으로 100% 확정할 수 없었다**
  (좌우 반전 비교 시 오히려 유사도가 낮아져 — 0.559 — 단순 수평 미러가 아니라 손으로 따로 그린
  두 행이기 때문). 잠정 배정은 **행1=Left, 행3=Right**로 문서화하되, godot-engineer가 인게임에서
  왼쪽 이동 시 캐릭터가 반대로 보이면 **SpriteFrames의 이름표만 맞바꾸면 된다**(재작업 없음).

### 1.4 행4~6 (godot-engineer 질문에 대한 답)

- **행4 = Attack, 4프레임, 단일 방향뿐** — 상/하/좌/우 방향별 공격 프레임이 원본 팩에 **존재하지 않는다**.
  현재 Player.tscn이 Knight의 Attack 행을 쓰지 않고 `WeaponPivot`+`WeaponSprite`(검 스프라이트 회전)로
  공격을 구현한 것은 이 제약을 이미 올바르게 우회한 선택이다 — **M1 게이트까지 이 방식 유지를 권장**.
  (행4를 쓰고 싶다면 "정면 공격 전용 1개 포즈"로만 쓸 수 있고, 다른 방향은 여전히 무기 회전으로
  처리해야 함 — 혼용은 비추천, 이질감만 커짐.)
- **행5 = Jump, 4프레임, 단일 방향뿐** — 이 게임에는 점프 메커닉이 없으므로 **미사용 권장**. 구르기(Roll)
  연출에 억지로 재활용하지 말 것 (포즈가 안 맞음). 현재 `roll.gd`가 RollGhost 잔상 이펙트만으로
  구르기를 표현하는 것으로 충분하다.
- **행6 = 4개의 개별 1프레임 포즈** (열0=Dead, 열1=Item, 열2=Special1, 열3=Special2) — 애니메이션이
  아니라 정지 포즈 모음. Dead는 `dead.gd`의 페이드아웃 연출에 정지 프레임으로 넣으면 시각적 이득이
  있지만(현재는 마지막 idle 프레임이 그대로 페이드), 필수는 아님.

### 1.5 원작 공격 프레임 제작 요청 (아트 바이블 반영용)

원작 도트로 교체할 때 필요한 물량 — GDD 9장 기준 "공격 4~6프레임":

| 항목 | 필요 프레임 | 비고 |
|---|---|---|
| 공격(4방향 각각) | 4~6f × 4방향 = 16~24f | 현재 팩은 1방향 4f뿐 — 부족분 전체 제작 필요 |
| 이동(4방향) | 6f × 4방향 = 24f | GDD는 6f 기준, 현재 팩은 4f — 프레임 보간 또는 재작업 필요 |
| 유휴(4방향) | 4f × 4방향 = 16f | 개성 동작(눈 깜빡임 등) 필수 — 현재 팩은 1방향 4f뿐 |
| 피격 | 2~3f | 원작 팩에 없음(플래시 이펙트로 대체 중, 유지 권장) |
| 사망 | 3~4f | 원작 팩은 1프레임(행6열0) — 쓰러지는 중간 동작 보강 필요 |

## 2. Slime — `Actor/Monster/Slime/Slime.png` (64×64, 16px 셀, 4열×4행)

`Actor/Monster/`에는 Knight 같은 `SeparateAnim` 원본 조각이 없어 **행별 의미를 100% 확정할 근거가
없다**. 아래는 행간 유사도 + "회색(그림자) 픽셀 수" 계측으로 추정한 결과이며 확신도를 명시한다.

```
행0 vs 행3 = 0.864 (유사) — 그림자 픽셀 10개대(작음), 둥글고 납작한 실루엣
행1 vs 행2 = 0.823 (유사) — 그림자 픽셀 34개대(큼), 위로 솟은 둥근 실루엣
그 외 조합 = 0.43~0.52
```

- **행0 = Idle (확신 중간)** — 낮고 납작한 반복 포즈, 관례상 행0=Idle.
- **행1 = Walk/Hop (확신 중간)** — 그림자가 커지고 몸이 위로 솟은 형태로, 통통 튀는 이동 동작에 부합.
- **행2 = 불확실** — 행1과 형태가 거의 같음(그림자량 동일). Attack(돌진/점프 공격)의 재탕이거나
  단순히 애니메이션 다양성을 위한 대체 프레임일 수 있음.
- **행3 = 불확실** — 행0과 형태가 거의 같음(납작함). 사망 직전 "짜부라짐" 연출에 어울리는 실루엣이라
  Dead 후보로 볼 수는 있으나, Idle의 변형일 가능성도 배제 못함.

### 2.1 현재 게임 구현과의 대조

`game/scenes/entities/monsters/Slime.tscn`은 현재 **열0을 행0~3에 걸쳐 세로로 잘라** `idle` 애니메이션
하나로만 쓰고 있다(= 행0열0, 행1열0, 행2열0, 행3열0 네 프레임을 순환). 공교롭게도 위 유사도 그룹
(행0≈행3, 행1≈행2)이 정확히 "AB AB" 순서로 배치돼 있어, 결과적으로 자연스러운 "수축→팽창→수축→팽창"
통통 튀는 루프처럼 보인다 — **의도한 결과는 아니었겠지만 시각적으로는 우연히 잘 맞물린다.** 굳이
바꿀 필요는 없다고 판단한다.

### 2.2 피격/사망 프레임 유무 — 결론: 없음

이 시트에는 색이 바뀌거나(빨갛게 물듦) 납작하게 터지는 등 **"피격"이나 "사망"임이 명확한 전용
프레임이 없다**. `monster_base.gd`를 확인한 결과 이미 이를 전제로 설계돼 있었다:

- 피격(`HURT`): `HitFeel.apply()` — 셰이더/모듈레이트 기반 흰색 점멸(스프라이트 프레임 전환 없음).
- 예고(`TELEGRAPH`): `_start_telegraph_flash()` — 빨간 점멸 tween.
- 사망(`DEAD`): `_play_death()` — `modulate:a`를 0으로 tween 후 `queue_free`(페이드아웃, 프레임 전환 없음).

**권장(현행 유지)**: 픽셀 포렌식만으로는 신뢰할 수 있는 히트/사망 프레임을 특정할 수 없으므로, 이미
구현된 **플래시(피격)+페이드(사망)** 방식을 M1 게이트까지 그대로 유지한다. 원작 도트 제작 시에는
"짜부라짐(사망 전조, 분열 몬스터이므로 GDD의 '방울 슬라임(분열)' 기믹과 연결되는 연출)" 전용
2~3프레임을 새로 그리는 것을 아트 바이블에 과제로 남긴다.

### 2.3 팔레트 스왑 변종안

Slime은 이미 팩 내에 `Slime2`·`Slime3`·`Slime4` 색상 변형이 존재한다(동일 골격, 색만 다름) —
지역별 슬라임 변종(예: 안개숲=초록 독슬라임, 설산=하늘색 얼음슬라임) 배정에 그대로 활용 가능.
골격 재사용 매트릭스에 등록.

## 3. 뿔토끼(horn_rabbit, 돌진형) 대역 추천

`monsters.json`의 `horn_rabbit`은 `attack_pattern_id: "charge"`(웅크림 예고 0.6s → 돌진 0.3s,
200px/s)로 이미 정의돼 있다. `Actor/Monster/` 중 사족보행 돌진형 후보를 실제로 열어 비교했다
(`docs/art/preview/monster_candidates_grid.png`).

| 후보 | 구조 | 평가 |
|---|---|---|
| **Racoon** (`Actor/Monster/Racoon/SpriteSheet.png`, 64×64) | 4×4, 사족보행, 둥글고 통통한 실루엣, 줄무늬 꼬리 | **1순위 추천**. 4프레임에 걸쳐 다리를 번갈아 뻗는 달리기 포즈가 뚜렷해 "돌진" 웅크림→박치기 텔레그래프에 대역으로 가장 자연스럽다. `GoldRacoon`(동일 골격, 금색 팔레트)이 이미 존재해 정예/변종 배정에도 바로 쓸 수 있음 |
| Mouse / MouseBlack (64×64) | 4×4, 사족보행, 긴 꼬리 늘어짐 | 2순위. 몸통이 더 가늘고 쥐에 가까워 "토끼" 인상은 약하지만 구조는 동일하게 재사용 가능 |
| Beast / Beast2 (64×64) | 4×4, 딱정벌레/게형 실루엣, 가시 등딱지 | 비추천. 곤충형이라 "귀여운 뿔토끼" 톤과 실루엣이 맞지 않음(GDD 8.1 "귀여운 실루엣" 기준에서 벗어남) |

**대역 배정**: `horn_rabbit` → `Actor/Monster/Racoon/SpriteSheet.png` (또는 `GoldRacoon`을 지역/정예
변종용으로 병행). 뿔은 플레이스홀더에서는 생략(팔레트 스왑 스크립트로 나중에 2px짜리 뿔만 얹는 것도
가능하나 필수 아님 — 어차피 원작 교체 대상).

행 구조는 Slime과 동일한 패턴(행0≈행2 매우 유사 0.947, 행1≈행3 유사 0.878)이 나타나 **행0=Idle,
행1=Walk, 행2=Idle 계열(또는 Attack), 행3=Walk 계열(또는 Hurt)로 잠정 추정**하되 확신도는 Slime과
동급(중간~낮음)이다.

## 4. 버섯돌이(mushroom, 포자 장판형) 대역 추천

`monsters.json`의 `mushroom`은 `attack_pattern_id: "spore_patch"`(접촉 12 + 장판 내 4/초 지속, 예고
0.7s)로, 이동속도가 20px/s로 느려 "제자리 고정형에 가까운" 몬스터다.

| 후보 | 구조 | 평가 |
|---|---|---|
| **Mushroom** (`Actor/Monster/Mushroom/mushroom.png`, 64×64) | 4×4, 빨간 반점 갓 + 회색 밑둥, 이름부터 일치 | **1순위 추천**. 형태 자체가 이미 "포자 장판"과 시각적으로 바로 연결됨(갓 아래로 포자가 퍼지는 상상이 쉬움) |
| Mushroom2 (동일 골격, 하늘색 팔레트) | 4×4 | 팔레트 스왑 변종 1순위 후보 — 안개숲(엘드우드) 지역 변종 배정에 바로 사용 |

행간 유사도는 행0≈행2(0.939)는 다른 몬스터와 같은 패턴이지만, **행1≈행3 유사도가 0.357로 낮아**
Mushroom은 Slime/Racoon과 다른 구조로 보인다 — 버섯은 이동하지 않는 고정형 몬스터라 "Walk" 행 자체가
약하고, 행3이 확연히 다른 실루엣(포자를 뿜는 듯 벌어진 형태로 추정)일 가능성이 있다. **행3을
포자 발사(spore_patch) 텔레그래프/공격 연출 후보로 우선 검토**할 것을 제안하되, 이 역시 육안 확인 후
확정 필요.

**대역 배정**: `mushroom` → `Actor/Monster/Mushroom/mushroom.png` (지역 변종은 `Mushroom2`).

## 5. M1 게이트용 Placeholder 규격

### 5.1 현재 기준 (16px 팩, 카메라 줌 2×)

- `Main.tscn`의 카메라 `zoom = Vector2(2, 2)` 확인됨 — 16px 소스가 화면상 32px처럼 보여 32×32
  월드 타일 그리드와 정합한다(`asset-sources.md`의 "16px 팩은 정수배 2× 확대" 원칙과 일치).
  **셰이더나 임포트 단계에서 별도 확대 처리 없이 카메라 줌만으로 밀도를 맞추고 있다** — 이 방식을
  M1~M2 내내 유지.
- 캐릭터/몬스터 콜리전 크기는 현재 코드 기준 대략 10×8px(스프라이트 안쪽 발밑) — 32×48 원작 전환
  시에도 피벗(발밑 중심)과 콜리전 비율 감각을 유지해야 함(5.2 참고).
- 텍스처 필터는 반드시 Nearest(픽셀 선명도 유지) — 임포트 설정에서 확인 필요(아트 바이블 3장 참고).

### 5.2 원작 32×48 전환 절차 (교체만으로 반영되도록)

1. **TileSet 교체**: `32×32` 원작 타일셋을 만들어 기존 TileMap 리소스의 소스 텍스처만 교체한다.
   타일 인덱스/오토타일 규칙을 원본과 동일하게 유지하면 맵 데이터(`.tscn`/LDtk) 수정이 불필요하다.
2. **SpriteFrames 교체**: 캐릭터/몬스터 `.tscn`의 `SpriteFrames` 서브리소스가 참조하는 텍스처 경로만
   `32×48` 신규 시트로 바꾸고, `AtlasTexture.region`을 32×48 셀 그리드에 맞게 재계산한다(셀 크기만
   16→32(가로)·16→48(세로)로 스케일, 행/열 개수와 애니메이션 이름은 1~4장에서 확정한 의미를 그대로
   유지). 프레임 수가 GDD 기준(이동6·공격4~6·유휴4)으로 늘어나므로 `frames` 배열 재구성 필요.
3. **카메라 줌 조정**: 32px 밀도로 올라가면 `zoom`을 2×→1×(또는 1.5×)로 낮춰 동일한 화면 커버리지를
   유지한다. 콜리전 셰이프 크기는 스프라이트 대비 비율을 유지한 채 그대로 스케일.
4. **한 씬 내 밀도 혼용 금지** 원칙(`asset-sources.md` §2)을 그대로 적용 — 교체는 지역 단위로 일괄
   진행하고, 16px/32px가 한 맵에 섞이는 과도기 상태를 남기지 않는다.
