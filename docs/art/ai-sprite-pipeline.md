# AI 도트 생성 툴 기반 애셋 파이프라인

> 기준: `docs/art/art-bible.md`(§1 비율·해상도, §2 외곽선·명암, §3 팔레트, §4 프레임 규격, §5 네이밍),
> `docs/brd/04-decisions.md` D-130~D-135(원작 아트 규격: 960×540 내부 렌더, **캐릭터 32×48px**,
> 타일·아이콘 32×32, **걷기 8 · 공격 6 · 대기 4(호흡) · 피격 2프레임**), `docs/art/asset-sources.md`
> (외부 애셋 등급 규칙), `docs/art/motion-design-reference.md`(타이밍 원칙).
>
> 이 문서가 다루는 범위: **AI 도트 생성 툴(PixelLab.ai, Ludo.ai, 고해상도 생성기)을 이 프로젝트에
> 어떻게 쓰고, 결과물을 어떤 기준으로 승인·반입하는가.** 실제 생성 작업은 각 서비스가 웹 계정을
> 요구하므로 **사용자가 직접 수행**하고, 이 문서는 ① 브리프 작성 규칙 ② 라이선스·기록 규칙
> ③ 품질 게이트 ④ 반입 워크플로를 정의한다.
>
> 세부 규격의 정본은 `docs/art/character-fin-spec.md`(32×48 규격·프레임별 ms·선딜/타격/후딜·
> 피벗 (16,43)·히트박스)이다. 이 문서의 셀 크기·피벗 기본값은 그 문서와 동일하며, 두 문서가
> 어긋나면 스펙 문서를 우선한다. (스펙 문서에 동봉된 프로그램 생성 시안 스프라이트는 채택 보류
> 상태 — 부록 Z 참고. 규격·타이밍 수치만 유효하다.)

## 1. 툴 역할 분담표

| 툴 | 역할 | 입력 | 출력 | 이 프로젝트에서의 용도 | 하지 말아야 할 것 |
|---|---|---|---|---|---|
| **PixelLab.ai** | 캐릭터 베이스 포즈·4/8방향 시트, 타일 생성(텍스트 프롬프트 기반) | 영어 텍스트 프롬프트(+ 옵션으로 참고 이미지) | 방향별/모션별 도트 스프라이트시트 PNG | **캐릭터 원화 확정 전 베이스 실루엣**(D-135 "주인공 1종 시안" 단계), 지역 타일 시안 | 특정 상용 게임 이름을 프롬프트에 넣어 "그 스타일로" 요청 금지(§2 참고) |
| **Ludo.ai** | 도트 1장(베이스 포즈)에 모션 프리셋을 적용해 애니메이션 아틀라스 생성 | PixelLab(또는 자체 제작) 베이스 스프라이트 1장 | 모션 프리셋이 적용된 프레임 시퀀스 PNG/아틀라스 + JSON(프레임 메타) | PixelLab이 뽑은 정적 베이스에 **걷기·공격·대기·피격 모션**을 입히는 2단계 | 베이스 실루엣 자체를 이 툴에서 새로 디자인하지 않는다(모션 적용 전용으로 한정 — 베이스가 매 모션마다 미세하게 달라지면 정규화 단계에서 지터로 걸러진다) |
| **Higgsfield(또는 동급 고해상도 생성기)** | 고해상도 일러스트/포트레이트 | 텍스트 프롬프트 | 고해상도 PNG | **타이틀 화면 일러스트, 캐릭터 포트레이트(대화창·엔딩 스틸), 홍보용 키비주얼**만 — 인게임 32×48 스프라이트 용도 절대 아님(픽셀 밀도·톤이 완전히 다른 별도 파이프라인) | 도트 게임 인게임 에셋으로 축소해서 쓰지 않는다(§2 art-bible §1 "한 씬에서 픽셀 밀도를 섞지 않는다" 원칙과 직결 — 고해상도 렌더를 다운스케일한 것은 도트가 아니라 뭉개진 사진이 된다) |

- 순서 원칙(D-135): **PixelLab 베이스 1종 확정 → 승인 → Ludo.ai로 모션 세트 확장 → 나머지 캐릭터·몬스터·타일**. 시안 승인 전에는 규격을 전면 확정하지 않는다(다시 그려야 할 위험을 줄이기 위함).
- 세 툴 모두 계정 기반 웹 서비스라 아트 디렉터(이 세션)가 직접 실행할 수 없다 — 브리프(`docs/art/brief-fin-pixellab.md` 등)를 작성해 사용자에게 전달하고, 사용자가 생성한 결과물을 받아 정규화·검수한다.

## 2. 라이선스·기록 규칙

### 2.1 새 등급 "AI-생성"

`docs/art/asset-sources.md` §1의 등급표(A/B/C/✕)에 **다섯 번째 등급을 추가**한다:

| 등급 | 조건 | 저장소 커밋 | 용도 |
|---|---|---|---|
| **AI-생성** | 사용자가 PixelLab.ai/Ludo.ai/Higgsfield 등에서 직접 생성. 해당 서비스 약관의 상업적 이용 조건을 사용자가 확인·기입해야 반입 가능 | 조건부(아래 2.2) | 프로토타입 + (약관이 상업 이용·재배포를 허용하는 한) 출시 버전 |

`asset-sources.md`를 갱신할 때는 이 표를 §1 뒤에 그대로 추가하고, 이 문서(§2)를 그 표의 상세
규정으로 링크한다.

### 2.2 `LICENSES.md` 기입 없이는 `game/assets/`에 넣지 않는다

AI 생성물은 다음 정보가 **모두** `docs/art/LICENSES.md`에 한 행으로 기록되어야 반입 가능하다
(기존 "반입 완료" 표 형식을 그대로 따르되, AI 생성물 전용 열을 추가한 하위 표를 신설):

| 필수 기입 항목 | 설명 |
|---|---|
| 반입일 | 정규화 스크립트를 돌려 `game/assets/`에 넣은 날짜 |
| 툴 · 플랜 | 예: "PixelLab.ai (Pro 플랜)", "Ludo.ai (Free 플랜)" — 플랜별로 상업 이용 조건이 다른 경우가 많으므로 반드시 플랜명까지 기입 |
| 생성일 | 실제 생성 실행 날짜(플랜 만료·약관 개정 시점 추적용) |
| 프롬프트 전문 | §3 브리프에서 실제로 사용한 프롬프트 원문(추후 재현·감사 가능하도록) |
| 상업적 이용 조건 | **사용자가 해당 서비스의 이용약관/요금제 페이지를 직접 확인한 뒤** 요지를 요약해 기입(예: "Pro 플랜 생성물은 상업적 사용·재배포 가능, 크레딧 불요" 또는 "Free 플랜은 비상업 전용 — 상업 이용 불가"). **AI 디렉터가 약관을 대신 추정해서 기입하지 않는다** — 확인 안 된 경우 "확인 필요"로 비워 두고 반입을 보류한다 |
| 위치 | 반입 등급에 따라 `game/assets/` 또는 `game/assets_local/` 경로 |

- 위 표가 비어 있는 열이 하나라도 있으면 **그 애셋은 `game/assets/`에 넣지 않는다.** `assets-inbox`
  브랜치에 올린 원본 PNG는 승인 전까지 그 브랜치에만 존재한다(§4 워크플로 참고).
- 상업적 이용 조건이 "재배포 금지"인 플랜(무료 플랜에 흔함)이면 asset-sources.md의 B등급과 동일하게
  `game/assets_local/`(git 제외)에만 둔다.

### 2.3 저작권 주의 — 프롬프트에 실명 금지

PixelLab/Ludo/Higgsfield 프롬프트에 **특정 상용 게임·시리즈·캐릭터 이름을 넣어 "그 스타일로"
생성 요청하지 않는다** — 예: "젤다의전설 스타일", "크루세이더 퀘스트 스타일", "포켓몬 스타일" 등
금지. `docs/art/motion-design-reference.md`가 이미 확립한 원칙(스타일 언어만 일반 서술어로
재서술, 실제 스프라이트·고유명사는 참조하지 않음)을 프롬프트 작성 단계에도 그대로 적용한다.
대신 일반 스타일 기술어(예: "cute chibi fantasy RPG top-down pixel art", "SD proportions,
2.5 heads tall")를 쓴다 — 구체 예시는 `docs/art/brief-fin-pixellab.md` 참고.

## 3. 수용 체크리스트 (품질 게이트)

생성물이 `game/assets/`에 들어가기 전에 아래 항목을 **전부** 통과해야 한다. 각 항목에 검사 방법
(육안/스크립트)을 명시한다 — 스크립트 항목은 `tools/art/normalize_ai_sheet.py`가 자동 검사·보정한다.

| # | 항목 | 기준 | 검사 방법 |
|---|---|---|---|
| 1 | 셀 크기 | 32×48px 정확 | **스크립트**: `normalize_ai_sheet.py`가 소스 셀 크기를 `--src-cell-w/h`로 받아 정확히 잘라내고, 출력 셀을 32×48로 강제 리사이즈하므로 최종 산출물은 항상 규격을 만족한다. 다만 소스 그리드 해석(열/행 개수)이 잘못되면 캐릭터가 잘려 보이므로 **정규화 후 미리보기 PNG를 육안으로도 반드시 확인**한다 |
| 2 | 네 방향 실루엣 즉시 구분 | down(정면)/up(뒤통수)/left/right가 실루엣만으로 구분됨 | **육안**: `<name>_preview.png`(4배 확대, 그리드선 포함)를 네 방향 나란히 놓고 비교. 얼굴 유무·투구 깃털 방향 등 방향 구분 장치(브리프 §1 참고)가 실제로 반영됐는지 확인 |
| 3 | 프레임 간 지터 없음(옷·무기 형태 유지) | 프레임마다 실루엣 위치·크기가 흔들리지 않음 | **스크립트 + 육안**: `<name>_report.json`의 `max_position_jitter_px`(발밑 정렬 후 위치 오차, 정상적으로는 정렬 자체가 0에 가깝게 맞춤)와 `max_silhouette_size_jitter_px`(실루엣 bbox 크기 편차 — **이 값이 핵심 지표**, 2px 초과 시 스크립트가 경고 출력)를 확인. 수치가 낮아도 무기 형태가 프레임마다 다르게 그려지는 경우가 있으므로 `<name>_preview_<방향>.gif`를 재생해 육안으로 이중 확인 |
| 4 | 1px 외곽선 | 순검정(#000000) 아님, art-bible §2 기준 잉크색 사용 | **육안**: 확대 미리보기에서 외곽선 색 스포이드 확인(또는 팔레트 양자화 리포트에서 외곽선 색이 art-bible §3 잉크 hex `#141b1b`로 스냅됐는지 확인) |
| 5 | 팔레트 32색 이내 | 지역별 32색 팔레트(art-bible §3) 안에서만 색 사용 | **스크립트**: `--quantize` 옵션이 art-bible.md §3 표에서 hex를 자동 추출해 최근접 색으로 강제 스냅한다. 초과분은 자동 보정되므로, 검사는 "양자화 전/후 이미지를 나란히 비교해 캐릭터가 지나치게 다르게 보이지 않는지"(색이 너무 많이 튀면 원본 색 설계 자체를 다시 요청) 육안 확인으로 전환된다 |
| 6 | 걷기 8 · 공격 6 · 대기 4 · 피격 2프레임 | D-133/D-134 기준 프레임 수 정확히 일치 | **스크립트**: 출력 파일명에 자동으로 `_<프레임수>f` 접미사가 붙으므로(`chr_fin_walk_8f.png`) 파일명만 봐도 즉시 확인 가능. 프레임 수가 기준과 다르면 반입 전 반려 |
| 7 | 피벗 발밑 기준 | 32×48 셀 안에서 발밑이 고정 좌표(기본 (16,43), `character-fin-spec.md` 재작성 전까지 이 값을 잠정 기준으로 삼음)에 정렬 | **스크립트**: `normalize_frame()`이 각 프레임의 불투명 픽셀 바운딩박스 하단-중앙을 목표 피벗 좌표로 강제 이동시킨다(정렬 실패 시 자체 테스트가 실패하도록 이미 검증됨). 육안 확인은 미리보기 그리드선 대비 발 위치로 교차검증 |

- 6개 항목 중 하나라도 반려되면 **PixelLab/Ludo 프롬프트를 조정해 재생성**하거나(브리프 §2 변형
  프롬프트 활용), 정규화 스크립트 인자(소스 셀 크기·팔레트 등)를 다시 맞춰 재실행한다.
- 최종 승인은 아트 디렉터(이 역할) + game-designer(히트박스·타이밍 정합성) 확인을 함께 받는다.

## 4. 워크플로

```
1. 브리프 작성(아트 디렉터, 이 저장소)
   └─ docs/art/brief-fin-pixellab.md 같은 프롬프트 문서 제공

2. 생성(사용자, PixelLab.ai / Ludo.ai 웹에서 직접 실행)
   └─ 브리프의 프롬프트를 그대로 복사해 실행, 결과 PNG 다운로드

3. assets-inbox 브랜치에 PNG 업로드(기존에 쓰던 반입 경로 그대로)
   └─ 원본 그대로, 가공 전 상태로 올린다(추적성 확보)

4. tools/art/normalize_ai_sheet.py로 정규화
   └─ 배경 투명화 → 팔레트 양자화 → 발밑 피벗 정렬 → 32×48 시트 생성
   └─ 동시에 미리보기 PNG(4배, 그리드선) + 방향별 GIF + 지터 리포트 JSON 생성

5. 미리보기로 검수(§3 체크리스트 7항목)
   └─ 반려 시 2번 또는 4번으로 되돌아감

6. 승인
   └─ LICENSES.md에 §2.2 표 형식으로 행 추가(이게 없으면 다음 단계 진행 불가)

7. game/assets/sprites/characters/<slug>/ 배치
   └─ 네이밍 규칙(art-bible §5)을 따름: chr_<이름>_<동작>_<프레임수>f.png

8. SpriteFrames 통합(godot-engineer)
   └─ AtlasTexture region을 32×48 그리드로 잘라 SpriteFrames 리소스에 등록
   └─ 이 단계는 이 세션 범위 밖 — 코드(.tscn/.gd) 수정 없음
```

- 3~4번은 여러 번 반복될 수 있다(생성물이 한 번에 체크리스트를 통과하는 경우는 드물다). 매
  반복마다 `assets-inbox`에는 새 파일명(버전 접미사)으로 올려 이전 시도를 덮어쓰지 않는다.
- 몬스터 팔레트 스왑 변종(art-bible §9 매트릭스)도 동일 파이프라인을 쓴다 — 베이스 골격을
  PixelLab/Ludo로 확보한 뒤 `normalize_ai_sheet.py --quantize`를 지역별 팔레트로 다르게 돌리면
  변종 색상 시트를 빠르게 뽑을 수 있다(단, 이 스크립트는 "이미 있는 색을 팔레트에 맞춰 스냅"하는
  용도이지 "색 자체를 창의적으로 재배색"하지는 않으므로, 완전히 다른 색상 콘셉트가 필요하면 생성
  단계에서 프롬프트로 다시 요청한다).
