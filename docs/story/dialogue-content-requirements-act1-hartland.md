## 1. NPC별 말투 한 줄 가이드

1막 하틀랜드 퀘스트 15개의 giver로 실제 등장하는 인물만 정리한다(characters.md 3.1절·main-storyline.md 2장 근거).

| NPC | 말투 한 줄 | 근거 |
|---|---|---|
| 테오(조사단장, 기능 NPC) | 감정을 드러내지 않는 실무형 안내자. 문장을 3~5어절에서 끊는다("짐부터 챙기자.", "조심히."). 개인 서사·감정 묘사는 절대 넣지 않는다 | main-storyline.md 77행("개인 서사는 만들지 않고 오직 구조적 기능만 수행") |

| 다미(마을 아이, 1회성) | 짧은 문장+감탄사. 울음을 참을 때 말줄임이 늘어난다(밝은 아이 톤은 유지) | main-storyline.md s07, world-bible 7.1 병치 규칙 |

- 공통 규칙(world-bible 7.3): 개인 서사 대사(호감도용)만 "밝음+무거움 병치"를 적용하고, 이 문서가 다루는 **퀘스트 실무 대사**는 짧고 기능적으로 유지한다(7.3 마지막 줄).
- 몽실이는 NPC 대사 노드를 갖지 않으므로 아래 2장 표에서 "0(대사 없음)"으로 표기한다.

## 2. 퀘스트 15개 × 상태별 필요 대사 노드

### 2.1 상태 정의

Dialogue Manager가 분기해야 하는 4개 상태:

| 상태 | 의미 | 트리거 |
|---|---|---|
| 수락 전 | 퀘스트를 아직 등록하지 않았을 때 giver와 대화 | `talk` 시 quest_state == none |
| 진행 중 | 퀘스트 등록됨, 목표 미달성 상태에서 giver 재대화 | `talk` 시 quest_state == active, objectives 미완료 |
| 완료 가능 | 목표는 달성했으나 아직 완료 처리(보상 수령) 전 | `talk` 시 quest_state == active, objectives 완료 |
| 완료 후 | 퀘스트 완료 후 같은 giver를 다시 대화 | `talk` 시 quest_state == completed |

기존 문서(main-storyline.md·quests-act1-hartland.md)는 "수락 전"과 "완료(컷신)" 대사만 확정해 두었다. **"진행 중" 재대화 대사와 "완료 후" 재대화 대사는 대부분 아직 존재하지 않는다** — 이게 이번 대사 시스템 작업(토스트 대체)의 실제 신규 작업량이다.

## 3. 대사 길이 상한

world-bible.md 7.2절을 그대로 이번 작업의 하드 제약으로 채택한다(신규 문서를 만들지 않음, 값만 재확인):

- **한 줄 14자 내외 × 최대 3줄** — 640×360 캔버스 해상도 역산 + WCAG CJK 권고 기준(리서치 03 카드 13).
- NPC 1회 대사(노드 1개)는 3줄 이내, 스킵 가능해야 한다.
- 이 상한은 이번에 신규로 쓰는 "진행 중"·"완료 후"·분기 리액션 노드에도 동일하게 적용한다 — 특히 로젤(예의체 존댓말)은 어미가 길어지기 쉬우므로 축약형 표현을 우선 검토한다.

## 4. 반복 방문 시 대사 변화 규칙

1. **상태 불변 구간은 로테이션하지 않는다.** 같은 상태(예: "진행 중")에서 giver를 몇 번을 다시 대화해도 고정된 노드 1개만 재생한다 — 리소스를 최소화하고, 상태가 실제로 바뀌었을 때만 대사가 바뀌게 해 "말이 달라졌다"는 신호를 명확히 준다.
2. **메인 체인은 "완료 후" 노드를 만들지 않는 게 기본값이다.** 대부분의 메인 퀘스트는 완료 즉시 다음 퀘스트가 자동 등록되므로(`on_complete.events`의 `register_quest`), "완료 후" 상태가 사실상 다음 퀘스트의 "수락 전" 상태로 즉시 대체된다. 표에서 "완료 후 0(N/A)"로 표시한 항목이 이에 해당한다.
3. **사이드 퀘스트 giver는 완료 후 `chat` 슬롯 풀로 자동 편입된다.** characters.md D-60이 이미 18인 NPC 전원에게 호감도 무관 잡담 슬롯(`npc_<지방>_<이름>_chat_<번호>`)을 배정해 두었으므로, S2~S4 완료 후 별도의 "완료 후 전용" 대사를 새로 짓지 않고 기존 chat/acq 풀로 넘긴다.
4. **일일 의뢰(게시판)만 완료 대사를 로테이션한다.** 매일 갱신되는 반복 콘텐츠이므로 단조로움을 막기 위해 최소 3개 문구를 순환/랜덤 배치한다(D1~D3 표의 "완료 후 3(신규)").
5. **1회성 NPC(다미)는 완료 후 재대화 대사를 만들지 않는다.** 몽실이 퀘스트는 1막 말미 1회만 발생하는 서사 비트이므로, 완료 후 다미가 마을에 상시 배치되는지 여부부터 결정이 필요하다(8장 참고) — 상시 배치가 아니라면 애초에 재대화 대사 자체가 불필요하다.

## 5. 로컬라이징 키 명명 제안

기존 규칙(quests-act1-hartland.md 0절 "대사 소유권 원칙")은 신규 퀘스트 전용 대사에 `quest_<퀘스트id>_line_<번호>` 하나만 정의해 두었다 — 상태 구분이 없다. 이번 작업부터 상태별 분기가 필요하므로 아래와 같이 **상태 슬롯을 추가하는 확장안**을 제안한다(기존 규칙과 충돌하지 않도록 슬롯만 덧붙임):

```
quest_<퀘스트id>_<상태>_<번호>
```

| 상태 slug | 의미 | 기존 규칙과의 관계 |
|---|---|---|
| `offer` | 수락 전 | 기존 `_line_<번호>`를 그대로 `offer`의 별칭으로 취급(하위호환, 재작성 없음) |
| `active` | 진행 중 | 신규 슬롯 |
| `ready` | 완료 가능 | 신규 슬롯 |
| `done` | 완료 후 | 신규 슬롯 |

- 예: `quest_side_heartland_festival_prep_active_01`
- 분기 선택지는 JSON이 이미 쓰고 있는 규칙을 그대로 따른다: `quest_<퀘스트id>_choice_<선택id>`
- 분기 결과 리액션은 `quest_<퀘스트id>_choice_<선택id>_reaction_01`
- 게시판 일일 의뢰 완료 로테이션: `quest_daily_heartland_<번호>_done_<로테이션번호>`(예: `quest_daily_heartland_01_done_01~03`)

이 확장은 `quest_ko.csv` 스키마 변경(상태 컬럼 또는 key 접두사 규칙 추가)을 수반하므로 8장 결정 필요 항목에 포함한다.

## 6. 언어 확장(다국어) 대응 여부

- **구조적으로는 이미 대응 가능.** characters.md 1.1절이 처음부터 "로마자 표음 slug + 상황 slug" 체계로 key를 설계했고, 5장의 확장안도 동일 체계를 따르므로 새 언어(EN 등) 추가 시 key 재설계가 필요 없다 — `quest_ko.csv` 옆에 `quest_en.csv`를 병렬로 두는 구조면 충분하다.
- **단, 텍스트 자체는 재작성이 필요한 항목이 있다.** world-bible 7.2절이 이미 "직역 가능"과 "톤 재창작 필요"를 태그로 구분하라고 규정해 두었다(리서치 03 카드 11). 이번 1막 신규 대사 중 재창작 필요 후보:
  - 메루 할머니 사투리 어미("~수?", "~라니까") — 직역 시 뉘앙스 소실, EN에서는 다른 방식(예: 짧고 무뚝뚝한 구어체)으로 재창작 필요.
  - 로젤의 예의체 존댓말/반말 전환(위급 시) — 한국어 특유의 존비속 체계라 EN에는 대응 문법이 없음, 톤(격식↔다급) 차이로 재창작.
  - 핀토의 허세→무안 리듬은 감탄사·말줄임 의존이라 대체로 직역 가능.
- **현재 시점 결론**: 지금은 KO 단일 언어로 진행하고, EN 착수 시점과 담당(narrative-writer 재창작 vs 별도 로컬라이저)만 결정하면 된다 — key 구조 자체를 바꿀 필요는 없다.

## 7. 대사 시스템 개발(development-order.md ⑥)과의 접점 정리

- **Dialogue Manager 연결**: 2.2절 표의 4개 상태(수락전/진행중/완료가능/완료후)가 곧 Dialogue Manager가 quest_state를 보고 분기해야 하는 조건 4가지다. godot-engineer에게 "이 4상태 분기가 전부"라고 명시할 수 있다.
- **토스트 대체**: 지금까지 완료 시 토스트로만 알리던 퀘스트들(대부분의 메인 체인)에 "완료 후" 노드가 없다는 것은 의도된 것이다(4장 규칙 2) — 토스트를 완전히 없애는 게 아니라, **giver 재대화 시에만** 대사로 대체하고 완료 알림 자체는 토스트를 유지해도 무방한지 결정이 필요하다(8장).
- **몽실이 분기 선택 UI**: 2.3절이 UI에 필요한 텍스트 5개(선택지 2 + 리액션 2 + 수렴 엔딩 기존 재사용)를 전부 열거했다 — UI 컴포넌트 자체(2지선다 팝업 형태)는 game-designer/ui-ux-designer 소관이며 이 문서는 텍스트 요구량만 확정한다.
