## 1. 앞으로의 순서

각 항목은 "동사 하나 = 단계 하나 = PR 하나"다. 단계마다 ① 계획(무엇을·어느 파일을·어떤 검증으로) → ② 구현 → ③ 헤드리스 검증 출력 첨부 → ④ PR → ⑤ 웹 데모 재배포 → ⑥ 사용자 플레이 소감 순으로 돈다.

| # | 단계 | 동사 | 완료 기준 | 담당 |
|---|---|---|---|---|
| ① | 애셋 인덱스 | "무엇이 있는지 안다" | `game/assets/assets.json`(경로·규격·출처·라이선스 등급) 자동 생성 스크립트 + `validate_tables.py` 연동. 참조되지 않는 애셋과 미등록 애셋을 목록화 | asset-wrangler |
| ② | 경험치·레벨업 | "적을 잡으면 강해진다" | `stats.json` 곡선으로 경험치 획득 → 레벨업 팝업·스탯 상승·HUD 갱신. 가이드 5-③ 항목 | game-designer → godot-engineer |
| ③ | 스킬 슬롯 1·2 | "Q/R로 기술을 쓴다" | 캐릭터 고유 메커니즘 중 핀 1종(패리 슬래시)만. GDD F2-5 | godot-engineer |
| ④ | 퀘스트 로그 UI | "무엇을 해야 하는지 본다" | 메인/사이드/의뢰 탭, 추적 전환. F5-1 | ui-ux-designer |

## 2. 가이드에서 새로 채택하는 규칙 3개

1. **계획 먼저.** 단계 착수 시 엔지니어에게 바로 구현을 시키지 않고, 수정할 파일·순서·검증 방법을 먼저 적게 하고 디렉터가 검토한 뒤 구현한다(가이드 3단계 `/plan` 원칙). 지금까지는 지시문에 파일을 명시하는 방식이었고, 앞으로는 에이전트의 계획 회신을 한 번 거친다.
2. **증거 없는 "고쳤습니다" 금지.** 완료 보고에는 실제 테스트 출력(GUT 수치·스모크 결과·콘솔 오류 수)을 반드시 붙인다. 이미 관례지만 규칙으로 명문화(가이드 6단계).
3. **파일당 500줄 상한.** 넘는 스크립트는 순수 계산(`*_calc.gd`)과 노드 로직으로 분리한다. 현재 `monster_base.gd`(약 830줄)·`inventory_menu.gd`가 초과 — ②~④ 진행 중 손대는 시점에 분리한다.

## 3. 채택하지 않는 것

- **PhaserJS 전환**: 위 표 1행.
- **사각형 placeholder로 되돌리기**: 전투 검증은 이미 실제 스프라이트로 끝났다.
- **Vercel**: GitHub Pages로 같은 결과. 필요하면 나중에 병행.
