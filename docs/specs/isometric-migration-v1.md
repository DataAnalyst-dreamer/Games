## 0. 먼저 — 엔진에 직접 물어본 변환식

수식을 추측하지 않고 Godot 4.4.1 에서 실측했다(`TileSet.tile_shape = TILE_SHAPE_ISOMETRIC`,
`tile_layout = TILE_LAYOUT_DIAMOND_DOWN`, `tile_offset_axis = TILE_OFFSET_AXIS_HORIZONTAL`,
`tile_size = (64, 32)`):

```
cell (0,0) -> (32, 16)      cell (1,0) -> (64, 32)      cell (0,1) -> (0, 32)
cell (1,1) -> (32, 48)      cell (2,0) -> (96, 48)      cell (0,2) -> (-32, 48)
```

즉 **셀 중심의 화면 좌표**는 폭 W·높이 H(=W/2)에 대해

```
screen.x = (cx - cy) * W/2 + W/2
screen.y = (cx + cy) * H/2 + H/2
```

역변환(`local_to_map`)도 엔진이 제공한다. 우리가 손으로 짤 변환식은 **데이터 마이그레이션용
한 번뿐**이고, 런타임은 `TileMapLayer.map_to_local()` / `local_to_map()` 을 쓴다.

## 1. 타일 규격 — 64×32 다이아몬드 (128×64 기각)

| | 64×32 | 128×64 |
|---|---|---|
| 640×360 뷰포트에 보이는 셀 | 약 10 × 22 = **220셀** (현재 정사각 20×11.2 = 224셀과 거의 동일) | 5 × 11 = 55셀 — **너무 확대돼 전투 시야가 무너진다** |
| FHD 정수 배율 | 640×360 **×3 = 1920×1080 정확** | 128px 셀을 살리려면 뷰포트 1280×720 → **×1.5 라 정수 배율이 깨진다**(`window/stretch/scale_mode="integer"`) |
| 아트 제작량 | 셀당 64×32 | 4배 면적 |

**권고: 64×32.** 결정적 이유는 취향이 아니라 `project.godot` 의 `viewport 640×360 + integer
stretch` 다 — 128×64 를 쓰려면 정수 배율을 포기하거나(도트가 뭉갠다) 뷰포트를 바꿔야 한다.

**지면 셀 = 32 월드단위 유지**(b1 D-206 의 성과). 지면에서 한 변 32wu 인 정사각 셀이 화면에서
64×32 마름모가 되는 것뿐이다. 캐릭터 핀 64×96(D-140)은 셀 1칸 폭 × 3칸 높이 — RO 비율과 맞는다.

## 2. 좌표계: (A) 화면 공간 물리 vs (B) 논리 격자 공간

### 2.1 두 안의 실체

| | (A) 화면 공간 물리 | (B) 논리 격자 공간 |
|---|---|---|
| 엔티티 `global_position` | 지금과 같은 **화면 좌표** | 격자 좌표, 렌더 시 변환 |
| 물리 | Godot 2D 물리 그대로 | 격자 공간에 별도 물리 또는 부모 노드에 등각 변환 |
| 스프라이트 | 그대로 | **부모에 변환을 걸면 스프라이트도 기울어진다** — 도트가 망가진다. 피하려면 스프라이트를 변환 안 걸린 별도 레이어에 두고 매 프레임 동기화 |

### 2.2 권고: **(A) 화면 공간 물리**

(B)는 Godot 과 싸우는 길이다. 부모 노드에 등각 변환을 걸면 콜리전은 올바르게 마름모가 되지만
**스프라이트가 같이 기울어진다.** 이를 피하려면 액터마다 "물리 노드 ↔ 표시 노드"를 쪼개고 매
프레임 위치를 동기화해야 하는데, 노드 수가 2배가 되고 단계 (a)에서 만든 Y-sort·발밑 그림자
배선이 전부 깨진다. 얻는 것은 "거리 계산이 자연스럽다" 하나뿐이고, 그건 (A)에서 **함수 하나**로
해결된다.

### 2.3 (A)의 유일한 진짜 문제와 그 해법

화면 공간에서는 세로가 절반이라 **거리가 비등방(anisotropic)** 이다. 화면상 같은 100px이라도
동서로 100px은 지면 3.1칸, 남북으로 100px은 지면 6.2칸이다. 그대로 두면 몬스터가 남북에서
올 때만 늦게 반응하고, `aggro_range_px` 원이 지면에서는 타원이 된다.

해법은 **지면 거리 헬퍼 하나**다(신규 `scripts/systems/iso_math.gd`):

```
지면 벡터  ground(d) = Vector2(d.x/2 + d.y, d.y - d.x/2)   # 화면→지면 정확한 역변환(iso_math.to_ground)
# (정정) 초안의 Vector2(d.x, d.y*2)는 항상 정확한 값의 √2배가 나오는 순진 근사였다 — 등방이라 테스트로는
# 안 잡히지만 모든 사거리가 1/√2로 줄어든다. SmokeIsoCoords §3이 화면(64,0)→지면 45.255를 고정한다.
지면 거리  ground_distance(a, b) = ground(b - a).length()
```

이걸 쓰는 곳은 **거리 비교를 하는 6군데뿐**이다:
`monster_base.gd` 의 aggro/melee/leash/whistle 판정, `monster_ai_calc.gd` 의 `should_leash`·
`is_in_melee_range`, `quest_trigger.gd` 반경, `quest_target_locator.gd`, `minimap_calc.gd`,
`quest_tracker_calc.gd`. 나머지(넉백 방향, 이동, 히트박스 겹침)는 화면 공간 그대로가 맞다 —
**보이는 대로 맞는 것이 액션 게임에서 옳다.**

이동 입력도 같은 변환을 거친다: 입력 벡터를 지면에서 정규화한 뒤 화면으로 되돌리면
세로 이동이 자동으로 0.5배가 되고, 대각(격자 축) 이동 속도가 균일해진다. `Player`·`MonsterBase`
가 공유하는 `move_and_slide()` 직전 한 줄이다(b1 §4.2 에서 세로 감쇠용으로 이미 식별해 둔
바로 그 지점들 — 그때 D-200으로 1.0을 넣어 비워 둔 자리가 이제 채워진다).

### 2.4 데이터 좌표 변환 — 전부 스크립트 가능

현재 좌표는 "32wu 정사각 지면"이다. 지면 셀 = `(x/32, y/32)` 로 읽고 §0 식으로 화면에 꽂으면
된다. `tools/iso_convert.py`(b1 의 `qv_scale2.py` 와 같은 allowlist + 재실행 가드 방식):

| 대상 | 변환 | 개수 |
|---|---|---|
| `world_objects.json` `position` | 지면→화면 | 17 |
| `world_layout_hartland.json` | **변환 불필요** — 이미 타일 좌표라 격자 좌표 그 자체다 | – |
| `Main.tscn` 노드 `position` | 지면→화면 | 13 |
| `elite_spawner.gd` `SPAWN_POS_GLOBAL_TILE` | **변환 불필요** — 타일 좌표 × `TILE_SIZE_PROTOTYPE` | – |
| 세이브 `player.position` | 지면→화면, `FORMAT_VERSION` 2→3 | 1쌍 |
| `combat.json`/`monsters.json`/`skills.json` 의 `*_px` | **변환하지 않는다** — 전부 **지면 거리**로 재해석하고 §2.3 헬퍼가 비교한다 | 0 |

마지막 줄이 핵심이다. b1 에서 타일 단위로 정규화해 둔 덕에 밸런스 테이블은 손대지 않는다.
`test_unit_scale_invariants.gd` 의 "타일 단위 거리 불변" 검사가 그대로 회귀 가드가 된다.

## 3. Y-sort · 충돌 footprint · 높이

- **Y-sort**: 등각에서도 화면 Y 가 커질수록 앞이므로 단계 (a) 규칙(`Main.y_sort_enabled`,
  `World.z_index = -2`, 발밑 원점)이 **그대로 성립한다.** 바꿀 것 없음.
- **여러 셀을 덮는 오브젝트**: 집·절벽처럼 2×2 이상을 덮는 물체는 그림의 발밑이 아니라 **가장
  앞쪽(남쪽) 모서리**를 기준으로 정렬해야 한다. `TileData.y_sort_origin` 과 소품 Sprite2D 의
  `offset` 으로 맞춘다. b3 에서 확립한 "노드는 발밑, 그림은 offset" 규칙을 그대로 쓰되 기준점이
  마름모의 남쪽 꼭짓점이 된다.
- **충돌 footprint**: 지면의 정사각 한 칸은 화면에서 마름모다. 현재의 `RectangleShape2D` 접지
  띠는 **`ConvexPolygonShape2D` 마름모**로 바꾼다(`world.gd:_add_static_band()` 한 곳 + b3 의
  `BlacksmithNpc.tscn` `SolidBand`). 액터 몸통은 2:1 타원 ≈ `CapsuleShape2D` 를 눕힌 형태.
- **높이(절벽)**: 등각에서 높이는 순수한 화면 Y 오프셋이다. h wu 높은 지대는 그림을 h px 위로
  올리고, 걸어 다니는 윗면의 충돌은 같은 마름모를 그만큼 올려서 둔다. 구현은 **고도별
  TileMapLayer**(layer0 = 지면, layer1 = +32wu …)로 나누고 각 레이어에 `position.y = -고도`.
  b2 의 "절벽 3행(윗면/정면/그림자)" 구성은 **폐기**하고 고도 레이어 + 마름모 벽면 세트로 간다.

## 4. 캐릭터 방향 — 8방향 권고 (D-202 재검토 필요)

등각에서 화면의 상하좌우는 **격자의 대각선**이고, 격자 축(북동·남동·남서·북서)이 화면의 대각이다.
현재 4방향(정면/후면/좌/우, left=right 반전)을 그대로 쓰면 플레이어가 격자를 따라 걸을 때
**스프라이트가 45° 어긋난 채 미끄러진다.**

| 안 | 원화 장수(반전 활용) | 평가 |
|---|---|---|
| 4방향 유지 + 격자 축에 매핑 | 3장 (현재와 동일) | 이동은 격자 축 4방향으로 제한해야 자연스럽다 — 액션 조작감이 크게 후퇴 |
| **8방향(RO 표준)** | **5장**(S·SE·E·NE·N) + 3장 좌우 반전 | 원화 3→5장, **1.67배**(2배가 아니다). 대각 이동이 자연스럽고 RO 계열 레퍼런스와 일치 |

**권고: 8방향.** D-202(4방향 유지)는 비스듬 2D 전제에서 내린 결정이라 등각에서는 근거가
사라진다. 증가분이 1.67배로 예상보다 작다는 점이 판단 근거다 — PixelLab 파이프라인
(`brief-fin-pixellab.md`)의 방향 수만 늘리면 되고 프레임 규격(64×96, 발 기준점 (48,112))은 유지.
**단계 iso-3 로 분리**하고, 그 전까지는 현재 4방향 아트를 8방향 중 가까운 쪽에 매핑해 돌린다.

## 7. placeholder 생성기 등각 버전 · 브리프 개정 초안

`tools/art/gen_quarter_tiles.py` → `tools/art/gen_iso_tiles.py`(신규, 기존은 b1~b3 재현용으로 보존).

- **핵심 프리미티브**: `diamond(cx, cy, w=64, h=32)` 마름모 지면, `iso_box(w, d, h)` — 윗면
  마름모 + **남서면·남동면 두 수직면**(명도 각각 92%/78%, 빛은 좌상단).
- 범위: 마름모 잔디 3종(풀 뭉치·흙 얼룩·자갈) / 흙길 오토타일(마름모 경계) / 물 / **절벽 높이
  세트**(윗면 마름모 + 남서·남동 벽면 + 모서리 4종) / 집 A·대장간(iso_box + 박공 두 경사) /
  나무(줄기 iso_box + 캐노피) / 게시판·우편함·비석·우물·바위·울타리(전부 iso_box 기반).
- 팔레트는 계속 `art-bible.md` §3 파싱(사본 금지).
- **브리프 개정**(`brief-quarter-view-gpt-image.md` → 등각 판): §1 스타일 블록의
  `3/4 top-down oblique view ... south-facing vertical surfaces` 를
  **`true isometric 2:1 dimetric projection, 45-degree diamond grid, both the south-west and
  south-east faces of objects visible, no perspective convergence`** 로 교체. §2 크기 표는 논리
  크기를 마름모 기준으로 재기입(지면 64×32, 집 A 128×160 등). 프롬프트 본문의 조형 묘사는 유지.
